# 读书地图｜阅读到真实地图的操作 SOP

## Version 1.0 · 2026-10-10 · 按书独立执行 · 配套《读书地图｜项目总 Guideline》

# 一｜什么时候启动，以及默认协作方式

触发语例子：“我正在读《史记》，帮我定位鸿门宴”“把玄奘这一章做到地图上”“现在把刘邦和项羽在这一年的行踪同时画出来”“导出本书可去的地点到 Google My Maps”。不要求用户使用固定口令。  
收到读书片段、截图、书名章节或历史问题后，先识别本次要回答的研究问题和地图类型（单人路线／多人同期／军事地理／同地历时／现代探访）。优先回答正在阅读的内容；不要每遇到地名就把整本书和全球历史数据库重做一遍。  
工作节奏：平时逐章增量收集地点与事件；当用户说“出图”“汇总本章”“定稿”“导出”时再进行相应级别的地图制图、质量复核和保存。关键信息缺失时按不确定性处理；优先给可用的部分地图与候选方案，不以琐碎问题阻断阅读。

# 二｜Step 0：每本书建立独立工作区

在总项目《读书地图｜历史地理阅读项目》下为每本书建立一个子文件夹，命名《书名》｜读书地图。新建该书的来源索引、地点表、事件表、路线假设表、地图成果目录；没有积累大量内容时，可先用一个 Google Sheet 多标签页加一个地图文件，避免目录过度工程化。  
书籍元信息至少记录：书名、作者/译者、采用版本、阅读章节或页码、讨论中的历史年代、地理区域、当前目标、使用的现代底图与外部历史地图来源、更新时间。每本书原始资料与专题成果独立保存，但人物、历史事件与地点通过跨书稳定 ID 连接到共享历史时空索引。  
新书默认阶段：Collecting（采集）→ Researching（考证）→ Draft Map（初图）→ Reviewed（校验）→ Approved（用户认可）；需重做时保留变更记录。

# 三｜Step 1：从阅读材料抽取原始事实

按章节或单次阅读提取：①原文地名及异体写法；②人物/军队/国家；③发生了什么；④时间表述；⑤行动前后顺序与方位线索；⑥原文/页码/截图与出处。建立 Source\_ID、Place\_Mention\_ID、Event\_ID，不直接在此步替原文决定现代地点。  
事实记录模板：Event\_ID｜书名/章节/页码｜原文字句或简短摘要｜人物｜原文地名｜文本所述时间｜前置/后续事件｜事件类型｜叙事属性（史书/小说/传闻/考古）｜出处链接或文件。  
遇到冲突时同时记下“作者说法”和“当前研究判断”。用户上传的是文字或图片时不得推断截图上辨认不出的字。存在异本、断句或译名差异，保留文本版本，不让地图反过来篡改原文。  
在轻量阅读模式下只记录关键节点：每个新地点优先做初步定位；没有时间时把疑点放入 Pending\_QA 队列，之后批量考证。

# 四｜Step 2：历史名称到现代位置的考证

为每一个 Place Concept 分配永久 Place\_ID。先核对古代名称、可能存在时期及历史地理单位；再查同期史料、历史地图/考古研究与历史地名数据库；最后定位今天的城址、区域或遗址坐标，严禁直接把同名现代城市当作古城坐标。  
检索路径建议：原文史料与注释 → 学术专著/论文/考古报告 → CHGIS、Pleiades、World Historical Gazetteer 等适用地域库 → 现代测绘和遗址管理机构 → 卫星底图与当地访问资料。每条核心推断至少保存一个可回溯来源；有争议时至少记录各主要方案的来源。  
确认空间形式：point（单点）、polygon（城址范围/古湖泊）、line（古路段/古河道）、area\_uncertain（不确定区域）或 unknown。WGS84 经纬度只对点位填写；一个“城址范围”不得仅凭方便导出就悄悄缩成精确中心点。若为了查看方便使用中心点，明确标为“展示用代表点”。  
对于迁都、城墙扩建、河道迁移、同名异地，按时期建立 Place\_Version（例如“汉长安城”和“唐长安城”）；保留 Place\_ID 之间的继承/邻接关系，而不是覆盖旧坐标。  
位置证据等级：A（精确可靠的遗址/证据）；B（区域可靠、点位不明）；C（多个有根据的候选）；D（文学/传说或缺乏可靠史地定位）。另设 Time\_Precision 与 Source\_Confidence，不混成一个分数。候选 A/B/C 使用 Hypothesis\_ID，均可展示。  
Gate 2 检查：①古名及年代对应正确；②坐标或范围与现代地形吻合；③是否误将现代行政区当古代地点；④有无迁移与同名误判；⑤可靠度与来源完整；⑥不确定处未被默认为精准定位。

# 五｜Step 3：构建相应时代的地理环境

先选地理时间切片（如公元228年前后，或汉/唐/现代三期）。优先以同一 WGS84 坐标投影历史河流、湖泊、海岸线、古城、山口与古道路；注明每项图层的年代跨度和来源。时间跨度不符的古地图仅可作为对照，不能默认为事件当年的环境。  
古代地形：山脉、坡谷等相对稳定的形态可以参考现代高程，但需要考虑泥沙、河道改线、填海、湖泊变迁、城址埋藏与现代工程。古代道路应由古道研究、交通地理、考古或文献佐证；可根据地形提示“可能通道”，必须标注推断。  
古代行政/政权：默认展示都城、郡县治所、重要聚落及相互隶属网络；只有证据足够时才打开范围图层。分别标记行政区域、军事占据、实际控制与文化联系；对边缘不确定区域使用渐变或虚线，不画伪精确国界。  
Gate 3 检查：资料年代与故事年代是否相容？有没有把现代黄河河道、现代海岸线、今日高速公路或今日国界投回古代？历史底图能否与现代位置对齐？不能可靠建立的历史图层就关闭并解释。

# 六｜Step 4：按事件时间重建人物轨迹

先建立严格的 Event\_ID 序列，不先画线。每条事件有 earliest\_date、latest\_date、time\_label、time\_precision、actor、Place\_ID、行为与原文出处。公元前纪年、农历/公历转换和跨年代日期须明确历法口径；无法精确换算时保留原文历法和阶段标签。  
在地图上按时间顺序标点；相同地点多次访问用相同 Place\_ID、不同时序 Event\_ID。路线由段（Route\_Segment）组成，每段链接 from\_Event\_ID / to\_Event\_ID，记录 travel\_mode（若可知）、segment\_status（已证实/推断/争议/未知）、reference\_source 与 geometry\_source。  
线型规范：来源直接支持且路径明确→实线；有地理合理性但缺少完整路径→虚线；只有出发与到达点而中段未知→仅连概括性方向箭头或留断点，并在图例标明；多条有根据的路线→保留独立 Route\_Hypothesis A/B/C，不能平均成一条“折中路线”。  
继承九州地图经验：先核实所有节点真实位置，再连线；线路遵从真实地形；跨区域交通与局部步行/山地路线分开；完整且有依据的徒步 trail 应按全程轨迹，而不是直线连接端点；不在仅有两个地名时凭空绘制逐弯古道。  
Gate 4 检查：起点、终点、途经点和时间方向无误；线路是否绕过不存在的山口/穿过同期不存在的桥梁；不同候选是否标识清楚；地图与事件表是否可逐条互相追溯。

# 七｜Step 5：按题材选用例模板

## A. 单人轨迹图（默认、成本最低）

输入：人物＋起止章节或时期。输出：真实地理底图上的分阶段节点、时间编号、移动方向、古今地名对照和关键事件；不确定路线可只标点。示例：苏东坡人生轨迹、李白游历。

## B. 多人物同期轨迹图

输入：人物 A/B/…、共同时间粒度（年/月/战役阶段）。以同一时间轴过滤事件，人物固定不同颜色；侧栏同时显示人物当前地点、状态和来源。如果某人的精确位置不明，应显示“本阶段活动区域/未知”，不可造出同一日的虚假同步精度。示例：楚汉相争。

## C. 军事地理图

在 B 的基础上加地形、高程、山口、河流、古道、营垒、城池、补给和政治控制；区分主力、疑兵、战略方向与实证路线。战争阶段切换优先于动画炫技。示例：诸葛亮第一次北伐。

## D. 同地多时代叠加

输入：研究地理范围＋对比时代。以固定现代坐标与比例尺加载多个时期的城址/河道/道路/地名；提供时代开关、透明度叠加、左右对照；同名城池在迁址后应分别呈现历史空间范围。示例：汉长安、唐长安和现代西安。

## E. 今日可到达的历史地点

在已考证历史点之外单列 Visit\_Point：今天可以抵达的遗址公园、纪念地点、观景处或通行道路节点；为“仅有大范围推定”的历史事件优先输出可解释的区域，而不是虚构精确旧址。

# 八｜Step 6：三种标准视图与图层设计

视图 1「现代定位」：现代真实底图＋历史地点/轨迹＋今日访问点，适合旅行；视图 2「历史重建」：与事件时代尽可能一致的自然地理、古城/道路、必要政治节点，适合理解原文；视图 3「古今比较」：统一坐标的透明叠加/滑块/并列同尺度，适合城市与河道变迁。  
图层按内容开关：历史自然地理、古城/古名、古代行政节点与势力范围、古道路/交通、人物/事件、现代地名/道路、访问点、争议方案。默认只显示与本次阅读问题相关的层，避免一次塞满。  
标注优先级按比例尺变化：大陆级→国家/区域/关键转折；区域级→历史城镇/山口/河流；城市级→城址及街区；遗址级→现存建筑与参观入口。符号与颜色跨版本稳定，图例跟随可见图层变化。

# 九｜Step 7：出图、复核与交互操作

先做 Draft Map：至少包括真实现代定位底图、被研究事件的可核对地点、时间序列、路线状态（确定/推断/争议）、地名双标签、数据出处。历史重建图层可按证据逐步加；切勿因为古地图数据暂缺而阻断基础轨迹图。  
Review Map：逐点检查“原文→地点表→实际经纬度→地图位置”；逐段检查“事件顺序→几何线路→实际山川”；查看缩放后标签遮挡；若古今地图不能精确配准，应展示“配准误差/示意”并避免做街道级结论。  
用户提出修改时，只改被指出的历史事实、位置或图层，不要让修正一处造成其他地点漂移。地图定稿必须记录版本号、修改范围、已知争议和地图来源；若用户明确说“替代保存”，只替换确认的成果，不擅自删除原始考证数据。  
静态输出要求：地理主体优先，不做宣传海报；全局图回答何处/何时/怎样走；必要时增加一张局部放大图。地图点号、事件时间线、颜色与 legend 一致。必要时保留古今对照图各一张。

# 十｜Step 8：制作 Google My Maps 可导入成果

至少生成两个数据出口：Research\_Places（所有学术点，包括未确定坐标、候选及不可达点）和 Visit\_Points（经过验证、适合现代地图落点的地点）。不要把 B/C/D 级不确定范围硬压成一个貌似精确的可导航坐标。  
Visit\_Points.csv 最低字段：Visit\_ID, Name, Latitude, Longitude, Historical\_Name, Historical\_Period, Related\_Event, Reliability, Historical\_Place\_ID, Visit\_Type, Visit\_Note, Source\_URL。经纬度必须使用 WGS84 十进制，CSV 为 UTF-8；同一历史地点可以关联不同现代可访问点。  
额外建议字段：Book, Chapter, Hypothesis\_ID, Historical\_Location\_Description, Time\_Label, Modern\_Address, Access\_Status, Access\_URL, Source\_Quote, Last\_Verified。名称面向手机查看，描述简短；可靠度要明示。  
生成后在 Google My Maps 新建个人地图→选择图层“导入”→上传 CSV 或连接 Google Sheet→指定 Latitude/Longitude 为定位列→指定 Name 为标题列→检查点位并按需要分层；Google My Maps 与普通 Google Maps 的功能不同，导入通常在 My Maps 完成，之后可在 Google Maps 中访问自己的地图。具体界面以当时官方产品为准。  
另外可以生成 Research\_Routes.kml（线与多边形）及 Visit\_Places.kml；KML 只承载被核实的几何与基本属性，复杂的时间动态、透明叠加和证据交互仍由研究地图保存，不假设 Google My Maps 能完整显示高级历史 GIS 功能。  
导出 QA：①所有可导航点经纬度数值有效且经纬顺序正确；②抽检地点在真实现代地图位置；③候选地点不被误当定点；④历史点与访问点差异有备注；⑤ CSV 导入后点数、名字、分类基本一致；⑥可访问性有最近核查说明。

# 十一｜Step 9：归档、复用与持续阅读

每次阅读新章：增量记录事件、地名、人物、考证来源和待考证问题；用稳定的跨书 Person\_ID、Event\_ID、Place\_ID 及来源关联复用既有记录。各书地图的本地 P/E/R/S 展示编号可以保留，但必须有跨书 ID 映射，不得拿两本书的 P001 当成同一地点。、H001；不用建设跨书主键。  
一章结束可导出当前阶段图；一本书结束固定提供书籍总图、历史地理说明、可导航地点 CSV，按需要再给专题军事图、同地历时图和 KML。Google Drive 只保留最终成果及必要版本，不把临时失败图混入正式目录。  
与《项目总 Guideline》出现冲突时，以最新获用户确认的 Guideline 为准；如果 SOP 因真实案例新增适用方法，应回写规则并标注变更日期。

# 十二｜必须执行的完成检查（Definition of Done）

事实与出处：重要地点/日期/路线可追溯；故事、传闻、史实未混同；争议方案保留；事件时间精度符合资料。  
地理：现代点位核对；迁移/改道/海岸变化按相应时期处理；地图底图真实；古道没有被现代导航路线偷换；历史面和现代参观点清楚区分。  
视觉：当前视图目的明确；多级信息不过载；时代和图层标签准确；时间线、点位、线型、图例一致；全局可读、局部可核查。  
交付：用户要求的专题图已生成并检查；数据源/已知不确定性写明；Google My Maps CSV（如用户要实地访问）可导入且经过点位抽检；定稿保存到对应书籍文件夹并记录版本。

# 十三｜示范执行：诸葛亮第一次北伐

起始问题：“把公元228年第一次北伐画出来”。先锁定史料版本与研究时期；提取汉中、祁山、箕谷、街亭等原始地名及赵云/邓芝、诸葛亮、张郃、马谡相关事件；为各古地名建立地点候选和现代对照。  
检查陇右地形、秦岭—汉中交通走廊、同期城址与政权节点。主力与疑军分开画，明确每段是直接史料支持还是后世推断；街亭有位置争议则并列候选。绝不直接用现代公路连接成“诸葛亮原路线”。  
在现代定位视图输出历史地点、今日可访问的遗址/纪念地点（先核实是否真实可达）与 CSV；在历史重建视图解释为何具体山口、河谷与城池影响行军；如果资料不足则先交付可信节点图，待补证据后再补路线。

# 十四｜开始新阅读时的复用提示词

“按 Google Drive《读书地图｜阅读到真实地图的操作 SOP》处理我正在读的《书名》，目前到第X章/第X页。先从文本识别事件、古地名和时间，建立可追溯的古今地名对应；按需要考证古代地理环境，再用现代真实地图呈现。存在争议就并列假设，不强行确定。当前请做【采集/定位/路线图/古今叠加/导出 Google My Maps】。”  
资料原则：按项目总 Guideline 执行。参考九州旅行地图 SOP 的地理定位、轨迹、legend 与核对经验，但不得把旅行日志的“实际到访”标准机械套用到历史事件的“史料发生”判断。

十五｜2026-10-12 补充规则 v1.1：公开历史地图复用优先（适用于所有书籍）  
原则：在自行重绘历史图层之前，必须先检索可公开访问、可追溯的历史地理图集、WebGIS、研究型数据库及学者/爱好者项目。优先利用可靠既有成果，把投入集中于人物、事件、证据与路线标注。不得因某个网站声称“据谭其骧”便免去来源核查，也不能把版权图幅擅自重发。  
执行次序：①确定目标年代、空间范围及地图比例尺；②寻找传统权威底本（例如谭其骧《中国历史地图集》相应时期）及公众可访问的数字化历史地图；③检查发布时间、制作机构、史料依据、年代适配、地图精度、数据下载/标注/嵌入功能、使用条款和访问稳定性；④优先选已配准且可叠加的地图服务；⑤不足时才自己制作有限的补充图层。留下平台名称、URL、版本、访问日期、底图来源、授权状态和已验证/尚待验证的功能。  
候选来源登记（仅供实测，不自动判定授权）：左图右史 https\://history-map.osgeo.cn/ ；观沧海 https\://ageeye.app.ditushu.com/ ；IKCEST春秋齐鲁图 https\://ikcest-drr.data.ac.cn/map/m030e ；历史地图集软件 https\://cadicex.github.io/history\_map/ ；谭其骧地图图幅浏览 https\://www\.dituji.com/lsdt/zglsdtj/chunqiuzhanguo/ ；复旦—哈佛 CHGIS https\://chgis.fas.harvard.edu/ 。CHGIS主要历史行政时序覆盖公元前221年至1911年，不得直接当作孔子时代前551年的完整政区底图。浏览可见≠可以抓取瓦片、下载、重分发或在其他应用嵌入；逐项查验许可。引用学术图集需注明书名、版次及图幅。  
十六｜2026-10-12 补充规则 v1.1：历史地图与现代地图的对齐、叠加及地理变迁  
目标：不仅表现人物当年的位置，还通过同一地球坐标下不同年代地理对象的变化，观察河道改迁、湖泊消长、海岸变化、聚落及城址迁移等。  
底本分为两类：A. 经过地理配准的历史图像/瓦片；B. 可编辑历史矢量数据（地点、河流、湖泊、政区）。优先已有地理配准成果；未经配准的扫描纸图必须用可证实的稳定控制点配准并记录投影、转换方法、控制点和误差。禁止因为画面似乎重合就宣称精确吻合。山峰/遗址也需检查是否具有确切点位；河流、湖岸、政区边线通常不是稳定控制点。  
阅读模式最少支持：①仅历史；②历史与现代透明度叠加（滑块）；③仅现代。数据条件允许时增加同尺度左右对比、年代切换、特定地理对象高亮差异。前提是底图在同坐标系中且配准质量足够。若当前使用的平台不支持原生图层叠加，保留外链及标记数据，尝试可合法使用的GIS工具制作对照，不把模拟切换器称为已交付的真实地图。  
不能只比较两幅年代跨度很大的图片就断言具体变迁年份。历史河道/湖泊等单列 Historical\_Feature\_ID、形状（point/line/polygon）、有效年代范围、来源、证据等级、位置误差与争议方案；古今差异以可靠文献、历史测绘、水文地貌或考古资料验证，不靠AI补画已消失湖泊或虚构河道。区分自然变化、现代水库/工程改变和地图绘制误差。根据证据不足可留空或只提供定性说明。  
十七｜2026-10-12 补充规则 v1.1：内部独立图层、阅读合并显示  
内部独立数据至少为：历史政治/行政地理、历史自然地理（古河、湖、海岸、地形）、交通及路线假设、现代地理对照、人物事件点。每条记录必须含日期范围、坐标/几何来源、历史证据与可靠性标签。阅读时默认合并为一张清晰的历史综合视图；层级依次为自然背景（最淡）—政治空间—交通线—人物事件点（最醒目）。人物事件点在古今模式切换时保持同一历史位置定义，现代代表点必须注明代表性质；图例同步标注实证、推测与争议。  
一书可设 H001 等专题背景图层，内部子层例如 H001-A政治、H001-B自然、H001-C交通、H001-D现代；编号在同一本书内稳定。用户只需一张可读地图，勿强迫为底层数据分别开四张地图；当专题扩大再开放子层开关。  
《匏瓜》试点：H001春秋晚期鲁国综合历史背景；P001孔子出生（鲁昌平乡陬邑，今尼山—鲁源村一带传统定位，精确城址待考）；E001前551年传统生年。候选底图优先测试春秋齐鲁专题图和左图右史，查核鲁国故城、尼山、沂河位置；能配准时再叠加现代底图，逐项考证春秋—现代水系差异。不预先画出确定古道或虚构诸侯国精确边界。  
新增验收：引用每个第三方底本时留来源和使用限制；古今对照必须说明所比年代、配准误差与证据等级；不能执行的功能标明待验证，不把设计效果图作为真实GIS成果。阅读中发现有效新工作法时先在具体书试点，再修订总则。

十八｜2026-10-13 补充规则 v1.2：读书地图五元素与通用 UI  
地图元素共五项，分三组管理。第一组「现代底图」：OpenStreetMap 标准地图（包括现代地名、道路、水系等，不是纯行政区划图）、OpenTopoMap 地形图（山地、高程）、不显示现代地图，三者单选。第二组「历史图层」：谭其骧《中国历史地图集》春秋《齐鲁》栅格图像，以及春秋诸侯国范围矢量示意图，各自独立开关和透明度。第三组「阅读标注」：本书的人物、事件、地点和后续路线、候选区域，独立开关，数据与底图分开保存。  
UI 采用现代底图／历史图层／阅读标注三组控制，不再同时保留「仅现代、古今叠加、历史重点」预设模式与重复的显示开关。现代底图单选项目已经包括「不显示」，不额外设置同义复选框。历史层的透明度仅在该层开启时可调整。默认历史矢量层关闭，谭图可开启，阅读点显示。导航「看齐鲁全域、返回鲁国核心区」单独保留，不改变图层。所有显示组合由实际开关决定，图例与界面保持一致。用户阅读时可按需同时显示全部图层，数据结构依然独立维护。  
《匏瓜》v0.6 已包含五类地图元素，但界面仍有重复控制；上述 UI 为已确认的 v0.7 设计规范，不能宣称 v0.7 已经实现。以后新增历史水系、古湖泊图层时，采用独立图层，不强行与谭图图像合并。

二十二｜2026-10-29 地图标记可点击性：图层遮挡事故复盘与防复发规范  
案例：《匏瓜》H001 地图 P002 东防标记在图上可见，却无法点击弹出信息；曾错误归因于缩放范围，直到核查 Leaflet 图层叠放顺序才找到问题。原因是代表不确定地望范围的 L.circle 在 L.circleMarker 之后绘制，同处可交互图层时后绘制的范围形状覆盖或拦截了标记的鼠标/触摸事件。修复于 v1.2：不确定性圈设置 interactive:false，且应先画圈后画点；不依靠改变地图视野回避点击故障。此类失败与坐标真实性是两项独立问题。  
【必须遵守】1）所有仅用于视觉提示的圆圈、缓冲区、装饰性图层、填色面及非交互栅格，明确设置 interactive:false；必要时为图层设置 pointer-events:none，避免覆盖标记。2）地图中的人物事件标记放在专门高于背景、历史面和辅助范围层的 pane，设置明确的 z-index；先绘制辅助几何，再绘制互动标记。3）可交互点绑定各自的 popup，提供明确且足够大的手机触摸目标；确保 marker 不被透明图层遮挡。4）用户反馈“看得到但点不开”时，首先检查事件拦截、图层顺序、pane 的 z-index、interactive 和 CSS pointer-events，然后再检查缩放、坐标和数据是否加载，禁止未经检查就认定为视野问题。  
【发布前验收】每次新增或修改 P 点后，逐个检查 P001、P002 及新增标记：标准地图、地形底图、关闭现代底图但开启谭图等组合下均能点击并弹出正确的对应信息；在手机触摸操作下也应验证。检查不确定范围圈自身不会弹窗或截获点击，且打开/关闭历史栅格、矢量图、切换透明度不影响标记交互。如无法执行真实浏览器/手机测试，明确写“代码检查通过，交互待实测”，不要声称已通过设备验收。  
【规模化 UI 原则】不得为每一个 P 点自动增加固定导航按钮：此前 v1.1 的“全部阅读地点 / P001 / P002”一组按钮在 v1.3 删除。新增地点只进入独立阅读标注数据层；已有“齐鲁全域/鲁国核心区”等区域导航可保留。未来大量地点优先考虑按需搜索与聚合，不让地图控件数量随地点数线性增长。

【2026-11-06 历史人物轨迹专题接入】涉及历史人物生平路线、往返同地、政权矢量叠加、互动 HTML 和现实旅行规划时，优先调用《读书地图｜历史人物人生轨迹与实地旅行 SOP v2.0》：https\://docs.google.com/document/d/17nrHxE1Y1qDw3\_HKWLG\_yeTnSSr0hae4DJ4VyoLITlU/edit 。本通用 SOP 仍是其他类型地图的原则基础；地理收藏仍调用其独立的专项 SOP，不在本处复制细则。

二十三｜2026-11-10 补充规则 v1.3：跨书、跨人物、乱序积累  
Step A 阅读采集：从当前书籍或片段中提取每条 Source\_Assertion\_ID，保存书名、版本、章节页码、原文或审慎摘要、叙事属性、当事人物、地名、原文时间及发生顺序。不因未读完整生平而跳过。  
Step B 实体解析：查找人物异名/字/谥号、地点历史名称及既有事件；优先复用 Person\_ID、Place\_ID、Event\_ID。无法确定同一实体时新建候选并标记待考证，不粗暴合并。每书内部展示 ID 与共享 ID 建立映射。  
Step C 乱序入年表：保存时间原文、最早/最晚可能日期、精度（年/月/季节/阶段/仅前后）及不确定性；以可靠的时间约束排序，允许同年顺序未知。早读的晚年事件与后读的早年事件正常插入，不重新编号全库。  
Step D 合并证据而非覆盖：同一活动可以引用多本书、多个人物；为各来源保留独立论断。相互矛盾的日期、地点、路线并列显示，给出当前判断与理由，保留历次版本和待决问题。  
Step E 地理建模：活动点与行军路线分开保存。明确区分史料确认地点、推定地点、争议候选、未知；仅在史料或可解释的地理证据支持时建立 Route\_Segment。只知道前后两处出现不得推断中间道路；需要时在地图显示缺失区间而非假线。  
Step F 按需生成地图：可筛选单人全部已知活动、某时期多人同期轨迹、某事件参加人物与路线、某一本书提供的证据层。地图上允许空白时期与定位不足记录，标注数据覆盖，不把未记录说成未发生。  
Step G 保存/核验：先更新书籍原始材料，再更新共享 ID/关系和年表，按需求生成/更新地图；核对跨书去重、来源回链、人物归属、时间区间、地点候选与路线可信度。不得改坏现有孔子及伍子胥 HTML 版本；实际地图文件更新另走版本化验收。  
Step H 收尾：按既有“标准最后一步”列出本批所有实际识别地点，主动询问是否加入地理收藏与是否增设标签，确认后调用《地理收藏｜Guideline 与 SOP》。

二十四｜2026-11-13 补充规则 v1.4：地形优先、历史水文与地图时间适配  
Step 1 研究问题归类：每次定位历史事件时，先辨认其地理解释依赖山脉／山口、河流／渡口、湖沼／洪泛、海岸线还是古城／道路。现代行政区仅作为数据过滤与现实定位字段，不作为默认研究底图。  
Step 2 默认底图（2026-11-14 再修订）：所有新书历史专题地图默认采用带有海拔分色的彩色地形底图，并叠加适度山体晕渲；低海拔绿、中海拔黄褐、高海拔偏浅灰/米白。不得将纯灰白的 Hillshade、无高度色阶的纯白底图作为默认。应优先使用真实 DEM 或可靠的高程分色服务，而不是任意把灰度阴影涂成彩色。现代地名、道路及密集图例默认不显示，OpenTopoMap 与 OSM 仅用于细节、现代位置或出行对照。Google Maps Terrain 的正式嵌入仍须经过官方 API、密钥、计费与授权审核，禁止直接抓取 Google 瓦片。  
Step 3 分别研究稳定与可变要素：大型山地用现代 DEM 作初步骨架，注意黄土沟壑、滑坡、冲积、筑坝、削坡和填海等局部变化；河流、湖泊、湿地、三角洲、海岸线及历史渡口按事件年代单独取证。  
Step 4 建立 Historical\_Feature：至少记录 Feature\_ID、历史名/类别、Valid\_From、Valid\_To、Time\_Precision、geometry\_type、几何或不确定范围、Source\_ID、版本/许可、定位可靠度、Hypothesis\_ID、与现代水文关系。缺少当期资料的状态为 unknown，不以现代河道替代。  
Step 5 选择时间切片：把事件时间与每个自然地理要素的有效年代比较，显示适用的历史切片及出处；不同时间精度只能做区间判断，不将两期水系平滑插值成“逐年变化”。历史水文、历史政区、人物事件分别控制，避免同一图上混用年代。  
Step 6 古今对照与路线复核：研究城池、渡口、关隘和行军时，明确标识古今水文位置差别。河流移位、湖沼消长可能改变道路可行性；不以现代桥梁、堤岸、通航河段或渡口推断古代路线。  
Step 7 数据与地图交付：每次只为当前涉及地区和年代增加足够证据支持的图层；源数据纳入跨书共用历史地理索引，个人地理收藏只记现实地点、作品与理由。地图给出采用的底图、DEM／水文来源、图层年代、精度、缺口与候选解释。  
Gate H 验收：①默认彩色地形必须能明确区分不同海拔等级，并体现山脊、盆地和河谷，不能是近乎全白/纯灰背景；②历史地点与名称压在底图之上且可见、可点击；③现代行政界、现代河道不冒充历史疆界与古河道；④历史水系与事件年代相容；⑤缺失和争议资料不被描绘为确定位置；⑥第三方数据源、许可、署名及可用性明确；⑦联网的实际浏览器验证各底图与点位，手机触控与 UI 不遮挡。仅代码检查不得称实际地图验收通过。

二十五｜2026-11-14 补充规则 v1.5：低标注地形底图与图层显示验收  
【优先级】本节是对第十八、二十章旧版“现代底图三选一”和第二十四章 Step 2 的更新；以后新建读书地图按本节执行，不再以 OpenTopoMap 作为必选默认。用户在个别项目中另行指定的底图偏好优先，避免强行统一。  
【默认设计（已由 v1.6 修订）】采用有真实高程数据支持的彩色海拔分层＋适度地形晕渲，而非纯灰白 Hillshade；尽量去掉现代地名、道路文字和等高线数字。低处绿，中海拔黄/黄褐，更高处褐/灰浅，具体色阶和海拔区间按制图区域与 DEM 数据源核准。Esri World Hillshade 可作为辅助明暗参考，但不能单独充当默认地形图；纯白大片不满足本规范。历史地点和事件的颜色、标签仍须清晰可见。  
【备选与控制（已由 v1.6 修订）】底图单选：彩色高程＋晕渲（默认）／彩色自然地形备用（如有授权）／OpenTopoMap 详细地形／OpenStreetMap 现代标准地图／关闭底图。不得以地图底色或植被颜色冒充实际海拔分级；单纯彩色自然地理图作为备用时要标明不等于 DEM 严格高程分级。历史政区、水文、路线与阅读点仍彼此独立。遵守数据源署名、服务政策和授权约束。  
【Google Maps 边界】Google Terrain 可以作为将来的正式接入方案，但必须通过 Google 官方 Maps JavaScript API 等授权方式，落实 API Key、密钥限制、计费、地图样式、服务条款、显示区域与交互兼容性；不能把 Google 的地图网页或瓦片 URL 当成免费可热链的 Leaflet 底图，也不能声称已有 Google 地形图能力。若用户未配置 API，则继续使用可合法调用的低标注地形服务。  
【显示层级】地图底图（瓦片） \< 历史背景/辅助范围 \< 可点击地点标记 \< 地名标签 \< 弹窗；地图内部与页面侧栏、标题、搜索等 UI 的堆叠上下文分离。装饰性缓冲区和不确定圈不截获点击。地图控件不得遮挡地点或阅读文本；移动端单独检查触摸目标与布局。不得依靠连续盲调 CSS z-index 代替检查外部样式资源、Leaflet pane 和地图初始化。  
【交付验收（已由 v1.6 修订）】默认彩色高程图必须实际渲染出跨海拔色差、清晰山地阴影和可见历史地点。逐个检查点位及其弹窗，切换到备用彩色图、OpenTopoMap、OSM 或关闭底图后仍可用；侧栏与图层绝不互相覆盖。记录地图 JS/CSS、DEM 瓦片加载、CORS 和服务错误；若默认源失败，应显式告警、切换可用备用源，不得呈现整幅白图却宣称成功。手机浏览器真实测试与无障碍触控需检查。未能联网实测时必须写“结构/语法已检，实际显示待验”。  
【示范及版本记录】《战国歧途》H001 v0.7 已采用纯地形晕渲默认选项及三处晋国韩赵魏基地标记；这是已归档的实现版本，不代表全部浏览器运行场景已经核验。经验来源于 v0.3—v0.6 连续出现图层和资源加载异常，今后在复用前需实测，不以一次代码修正代替完整回归。地图的源数据、研究结论与现实地理收藏不因更换底图而改写。

二十六｜2026-11-14 补充规则 v1.6：必须显示海拔高度颜色（覆盖 v1.5 灰白晕渲默认方案）  
【用户确认的默认视觉】“地形图纯白的不行，需要显示高度的颜色”。读书历史地理地图的默认目标是彩色高程地形图（hypsometric tint）与适度阴影共同表达高低差；不是白底、纯灰度 Hillshade、带大量地名/道路的现代地图，也不是单纯按地表植被上色。不同海拔应可通过绿色—黄褐色—褐灰色—浅色区分，图例可简单解释低至高，但没有实际量化核对时不得伪造精确海拔刻度。  
【数据和可追溯性】优先使用有来源和编码说明的 DEM 高程数据。当前可选 Mapzen / AWS Terrain Tiles 的 Terrarium 格式，其海拔解码公式为 meters \= red\*256 \+ green \+ blue/256 − 32768；按绝对高程分色并计算地形阴影，必须正确注明来源及子数据集署名。数据 URL：https\://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png 。参考：https\://www\.mapzen.com/blog/terrain-tile-service/ 。不同地区的 DEM 精度不一，现代高程并不自动复原历史河川、湖泊或人工改造前地貌。  
【底图模式】默认彩色高程＋地势晕渲、无现代地名/道路标注；保留彩色自然地理备用、OpenTopoMap 细节、OSM 现代位置和无底图选项。仅在默认 DEM 不可用时切换备用底图，并告警；备用地图若非严格高程分层，应注明区别。密集现代地名、行政区界和路线不得默认叠加，不因换底图丢失本书已有 P/E 标记。  
【Google Maps】需要 Google Maps 地形图时，依法采用官方 Maps JavaScript API 及账户授权、Key、费用、区域设置，取得有效接入后再谈默认；不直接热链它的瓦片，不假称可以通过颜色更改获得真实的 Google Terrain 高程数据。  
【体验与验收】在真实联网的电脑和手机浏览器核验：①山体高度颜色差别清楚、不是大片白/灰；②瓦片跨边界连续、缩放不出大片空白；③每一处历史地点在背景之上，可点开自己的弹窗；④弹窗和侧栏不被瓦片遮盖；⑤底图切换后仍能显示各历史标记；⑥外部 DEM 瓦片 CORS/权限失败有提示或自动切换，而非静默空白；⑦来源署名与数据可信度准确。只有语法/结构检查时，标注“实际瓦片加载和移动端交互待验证”，不能替用户完成浏览器验收。  
【版本溯源】《战国歧途》H001 v0.7 的 Esri World Hillshade 纯灰白底图因视觉不足被否定；v0.8 改为以 Mapzen/AWS 数字高程着色的彩色地形方案，备选 Esri 彩色自然地形（旧服务）、OpenTopoMap 和 OSM。v0.8 的程序实现及资料归档不代表已完成联网设备实测，必须据实际反馈迭代。
